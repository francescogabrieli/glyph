# `.glp` v0.1 Specification

`.glp` v0.1 is a compact, deterministic, machine-readable instruction format for coding agents.

It encodes compact operational instruction semantics.

It is not a lossless encoding of arbitrary Markdown.

Product requirements, API contracts, and implementation notes may be classified in reports but are not automatically encoded unless they map to registered semantics or custom rules. Operational clauses that cannot be structured safely are retained in `preserve[]`; arbitrary prose is never copied into that section.

## Scope

`.glp` exists to encode instruction semantics such as:

- execution flow
- required behaviors
- prohibited behaviors
- confirmation-required behaviors
- recommended commands
- lightweight repository context

It is designed to work alongside Markdown compatibility emitters, not replace all project documentation.

## File Encoding

- UTF-8 text
- Unix or Windows newlines are acceptable
- Deterministic section ordering is recommended for generated output

## Version Line

The first non-comment, non-empty line must be one of:

```txt
glyph/0.1
g/0.1
```

`glyph/0.1` is the readable header.

`g/0.1` is the compact header used by the `ultra` profile.

Files with any other header are invalid.

## Allowed Sections

`.glp` v0.1 supports these semantic sections:

```txt
agent <value>
goal <value...>
stack[...]
scope[...]
flow[...]
cmd.<name> "<command>"
must[...]
deny[...]
ask[...]
policy[...]
preserve[...]
```

Short aliases are valid for compact files:

```txt
s[...]   -> stack[...]
sc[...]  -> scope[...]
f[...]   -> flow[...]
m[...]   -> must[...]
d[...]   -> deny[...]
a[...]   -> ask[...]
p[...]   -> policy[...]
x[...]   -> preserve[...]
```

No other top-level sections are defined in v0.1.

## Syntax

### Scalars

```txt
agent backend
goal maintain_improve fastapi_backend postgres
```

- `agent` stores one opaque identifier or label.
- `goal` stores whitespace-separated tokens.

### Lists

Single-line list form:

```txt
stack[python,fastapi,postgres,pytest]
```

Multi-line list form:

```txt
must[
  read_before_edit
  run_tests_before_done
]
```

Rules:

- commas and newlines both separate values
- surrounding whitespace is ignored
- empty list values are ignored
- values are treated as plain text tokens

### Commands

```txt
cmd.test "pytest"
cmd.lint "ruff check ."
cmd.dev "uvicorn app.main:app --reload"
```

Rules:

- command names follow `cmd.`
- the remainder of the line is the command value
- generated output should quote commands

### Structured Policies

`policy[]` holds repository-specific directives that Glyph can represent with a deterministic action/target model:

```txt
policy[
  must p_0123456789ab action=require target=permission_check scope=page.tsx except=layout.tsx risk=high tag=security
]
```

The first two values are category and identifier. `action` and `target` are required. `scope`, `condition`, `except`, and `tag` may be repeated. Values containing whitespace must be quoted. Generated identifiers use the `p_<sha12>` form and are derived from policy content, not source paths or line numbers.

Ultra files use the aliases `a`, `t`, `s`, `c`, `e`, `r`, and `g` for those fields.

### Preserved Operational Directives

`preserve[]` retains an operational clause verbatim when Glyph cannot represent it with sufficient confidence:

```txt
preserve[
  unknown x_0123456789ab risk=medium -- "Exact source-faithful operational clause."
]
```

The category is `must`, `deny`, `ask`, or `unknown`; only `risk` and repeatable `tag` fields are allowed. Generated identifiers use `x_<sha12>` and are content-based. `preserve[]` is not a general Markdown escape hatch: documentation and non-operational prose do not belong there. Source provenance is kept in reports and lockfiles, not in `.glp` text.

### Comments

Lines whose first non-whitespace character is `#` are comments and ignored.

Example:

```txt
# generated by glyph
glyph/0.1
must[run_tests_before_done]
```

Inline trailing comments are not defined by v0.1.

## Section Semantics

### `flow[]`

`flow[]` describes recommended execution order or workflow stages.

Typical values:

```txt
flow[read,plan,minimal_change,test,report]
```

Agents or adapters may use this to bias execution order, but `flow[]` is advisory unless a runtime chooses to enforce it.

### `must[]`

`must[]` encodes required behaviors.

Example:

```txt
must[read_before_edit,run_tests_before_done,report_changes]
```

### `deny[]`

`deny[]` encodes prohibited behaviors.

Example:

```txt
deny[secrets_commit,prod_config_write]
```

### `ask[]`

`ask[]` encodes actions that require confirmation or approval before proceeding.

Example:

```txt
ask[destructive_ops,schema_changes]
```

### `stack[]`

`stack[]` stores compact technology or environment tags.

Example:

```txt
stack[python,fastapi,postgres,docker,pytest]
```

### `scope[]`

`scope[]` stores lightweight path or area hints.

Example:

```txt
scope[src/,tests/,migrations/]
```

### `cmd.*`

`cmd.*` stores recommended commands for install, test, lint, build, migration, or repository-specific workflows.

## Metadata

Arbitrary metadata blocks are not part of `.glp` v0.1.

If additional metadata is needed, it should live in adjacent files, reports, or a future versioned spec extension.

## Registered Rules And Custom Rules

`.glp` does not require every rule ID to be built into Glyph.

Behavior:

- known registered semantics may be rendered with human-readable Markdown sentences
- unknown rule IDs may still appear in `must[]`, `deny[]`, or `ask[]`
- unknown rule IDs are preserved as opaque identifiers
- Markdown rendering may fall back to the raw rule ID when no registry entry is available

This allows repository-specific custom rules without changing the core file grammar.

## Rendering Expectations

Generated renderers should be deterministic.

For the same manifest, renderers should produce stable output order for:

- `stack[]`
- `scope[]`
- `flow[]`
- `cmd.*`
- `must[]`
- `deny[]`
- `ask[]`
- `policy[]`
- `preserve[]`

Markdown rendering should make clear that it preserves encoded operational semantics, not original prose.

## Parsing Errors

Parsers should reject at least these cases:

- missing or invalid version line
- unknown top-level sections
- malformed `cmd.*` entries
- unclosed multi-line blocks
- unrecognized non-empty syntax lines

Parsers may provide line-numbered errors.

## Compatibility Rules

`.glp` v0.1 is intended for progressive adoption.

Compatibility expectations:

- repositories may keep `.glp` as source of truth and emit Markdown fallbacks
- agents that do not support `.glp` can still consume rendered or emitted Markdown
- agents or adapters may inspect `.glp` through CLI or MCP without reading it directly
- future runtimes may support `.glp` natively if they honor `flow[]`, `must[]`, `deny[]`, `ask[]`, `cmd.*`, `stack[]`, and `scope[]`

`.glp` v0.1 does not define:

- binary encoding
- network transport
- hosted services
- LLM behavior guarantees
- native runtime support claims for any specific agent

## Security Considerations

`.glp` can encode safety-relevant instructions, but the file itself does not enforce runtime behavior.

Consumers should treat at least these categories as security-relevant:

- secret handling
- credential exposure
- production configuration changes
- destructive operations
- schema or migration approval
- deployment approval

Consumers should not silently drop safety-critical `deny[]` or `ask[]` rules during selection or rendering.

Consumers must also retain every `preserve[]` directive during task selection. A renderer must label preserved content as retained wording rather than presenting it as a structurally understood policy.

Unknown rule IDs with security implications should fail closed or surface a warning rather than being silently discarded.

## Examples

### `minimal.glp`

```txt
glyph/0.1
must[read_before_edit]
```

### `safety.glp`

```txt
glyph/0.1
deny[secrets_commit,prod_config_write]
ask[destructive_ops]
```

### `testing.glp`

```txt
glyph/0.1
flow[read,test,report]
cmd.test "pytest"
cmd.lint "ruff check ."
must[run_tests_before_done,lint_before_done,report_verification]
```

### `repo-specific.glp`

```txt
glyph/0.1
stack[python,postgres]
scope[src/,tests/]
must[route_tenant_reads]
ask[approval_for_billing_changes]
```

### `task-selection.glp`

```txt
glyph/0.1
stack[python,pytest,postgres]
flow[read,plan,minimal_change,test,report]
cmd.test "pytest"
must[read_before_edit,run_tests_before_done,report_changes,report_verification]
deny[secrets_commit]
ask[destructive_ops,schema_changes]
```

For a task such as `fix failing tests`, a selector may emit a reduced manifest, but safety-critical rules such as `secrets_commit` and `destructive_ops` should normally remain included.
